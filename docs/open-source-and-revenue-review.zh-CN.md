# 完全开源与商业收入兼容性分析

分析日期：2026-11-10。对象：当前工作区版本，包含尚未提交的改动。

本次检查覆盖桌面端页面和操作入口、Tauri 命令、安装下载、供应商配置、本地网关、中文与权限辅助、技能安装、账号钱包、代理管理、第三方源码集成、打包和现有 CI。属于静态代码审查，没有调用生产账号、支付或节点服务，没有修改业务代码。线上坚果账号、模型计费、支付回调、订阅签发和节点控制后端不在当前仓库中，不能据此认定线上已经存在或不存在相应防护；也没有完成全部 Git 历史及二进制的密钥审计。

## 1. 建议采用的商业定位

**把整个桌面助手开源，允许免费安装、自带 API Key 和自带代理；收入主要来自坚果托管模型服务、可控的托管网络资源、部署支持与维护。**

当前项目最适合成为模型服务的使用入口。安装器、中文设置、供应商切换、本地协议转换和公共技能安装都可以公开。用户付费购买的是你持续提供的算力、带宽、稳定性和服务，而这些资源不会因为客户端代码公开就自动免费。

需要接受的变化：有人会自行编译、移除坚果入口、接入其他供应商，甚至合法出售合规的衍生版本。标准开源许可证无法保证所有用户都从你这里消费，也无法禁止所有竞争者。应保护的是服务成本、品牌身份和服务体验。

“完全开源”有两种范围，必须在发布文案中说清楚：

- **本仓库完全开源**：包含桌面端及坚果接入代码；当前仓库之外的商业后台可以继续独立运营。不能因此宣称整套商业系统都已开源。
- **整套产品完全开源**：还需整理并开放模型网关、计费、钱包和订阅后台。仍然可以收费运营官方实例；公开的是代码，生产密钥、用户数据、上游账号、节点凭证、支付与签名私钥不属于开源内容。

如果选择第二种，自建用户承担自己的模型、带宽、运维和支付接入成本，官方托管版本仍然有收费价值。

## 3. 优先改造点及代码证据

### P0：把资源授权和成本控制放到服务端

**现状证据**：

- src/main.ts:2176 的 requireNutSubscriptionAccess 进行本地权益判断；2208 启动计时器，2227 的 reportNutProxyTraffic 汇总本机节点 todayUp/todayDown 并上报。
- src-tauri/src/lib.rs:2445 的 installer_proxy_billing 把客户端提供的 cumulativeBytes 发送到 /installer/proxy/start 或 report。
- src/main.ts:1677 的安装流程以 billNutUsage: false 开启代理；已有代理开启时，安装流程还会停止本机计费监控。这可以是有意的免费安装政策，但不能承担资源隔离的职责。
- 坚果订阅地址会交给本机 v2rayN。隐藏输入框、删除本地订阅或定时停止 Core，均无法保证节点凭证不被其他客户端继续使用。

**建议改法**：

1. 每个账号签发独立的订阅身份及节点访问凭证；避免共享一个长期可用的全员订阅或节点身份。当前仓库不足以判断线上是否共享，需要后台确认。
2. 开启托管服务前，由服务端原子地确认权益、收费或预留额度，再签发可用凭证；同一账号同一计费日的重复启动保持幂等。最终入口必须验证服务端权益，不能只依靠“调用 start 接口”的客户端约定。
3. 节点或可信网关负责统计真实流量、限制并发和额度；达到上限、欠费或撤销后在资源侧拒绝。客户端上报仅用于界面刷新及诊断。
4. 凭证短期化，并设计有效期、刷新和撤销；订阅 URL 过期不等于已经导出的节点凭证失效，节点也需要可撤销的身份。
5. 安装加速优先改成指定文件的下载镜像/缓存。若必须提供免费网络通道，使用独立的限额凭证和可控出口；把允许的目标、用量和有效期落实到服务端，不能仅在界面声称“仅限安装”。
6. 上线前让修改过的客户端或其他代理客户端连接测试：跳过流量上报、修改本地时间、重复启动或复制订阅，都不能获得超出服务端权益的资源。

这是最直接影响开源后收益的一项。闭源客户端同样可能被改动，因此修复它也会改善当前商业版本。

### P0：拆分卡密的多重权限

**现状证据**：src/main.ts:1457 的一键配置把登录卡密用于坚果 API Key；个人中心明确展示“当前卡密即 API Key”。wallet.rs 使用 accountId + mainKami 创建和查询订单；lib.rs:2261、2279 将卡密放入余额/用量查询参数。

**建议改法**：

- 卡密作为首次兑换或旧账号迁移凭证；登录后使用可过期、可撤销的账号会话。
- 模型调用使用单独的 API Key，可以设模型、预算和并发上限，并单独轮换。第三方客户端获得模型 Key 后不应因此获得充值核销、账户管理或代理权限。
- 代理使用独立凭证；钱包与账户管理使用账号会话。服务端从会话推导身份并校验订单归属，不以客户端传入 accountId 为授权依据。
- 把匿名 site-config 与登录后的私有权益响应分成明确的字段白名单。当前客户端接收宽泛的字符串字典，并合并两类配置；服务端必须保证匿名接口永不返回订阅、节点身份或个人凭证，客户端也不应把这些内容持久化进公共配置缓存。
- 余额、用量等接口不再把长期凭证放入 URL；日志和错误信息统一脱敏。原有密码 SHA-256 传输契约也需要后台核实防重放、密码哈希存储和限速策略，不能从当前客户端推断服务端的具体实现。
- 保留已有 DPAPI/钥匙串能力，并使用它保存助手自身凭证。写给 Codex/Codex++ 的明文 Key 应收紧文件权限、限定用途；配置备份也含敏感内容，需要保留期限和清理入口。
- list_codexpp_providers（lib.rs:3256）当前会返回完整 apiKey 到前端。列表默认仅返回 hasApiKey 和掩码；模型检测、切换等操作在 Rust 端按 providerId 读取凭证。

### P0：支付与模型扣费后端需要专项核实

wallet.rs 已有 HTTPS、禁止支付请求重定向、收银台域名校验、返回字段白名单等可保留设计。但是客户端传入的 value、custom、accountId、orderNo 都不能作为可信依据。

后端需要确认：金额/点数映射从服务器套餐生成；采用整数分和定点额度记账；支付回调验签并匹配商户、订单和金额；重复回调只入账一次；订单查询和核销按用户授权；卡密核销原子且一次性。客户端显示“已支付”不能触发充值入账。支付成功返回后的轮询只是获取服务器结果。

模型请求的认证、限额和扣费也必须在官方模型网关完成：并发预留预算、防止余额透支、失败/取消/流式中断有一致的结算规则，且不把供应商根 Key 发到桌面端。当前仓库只展示预存额度用途，不能验证线上模型计费正确性。

### P0：补齐许可证与第三方分发边界

根目录没有项目自身 LICENSE；package.json / Cargo.toml 也未声明项目许可证。仅将仓库设为公开，并不完整授予使用、修改、再分发的开源权利。package.json 的 private: true 只是防止发布 npm 包，可以保留，不是闭源开关。

建议先确认自有代码、素材与贡献的权利来源，再选择并填写许可证：

| 选择 | 适用目标 | 实际限制 |
| --- | --- | --- |
| GPL-3.0 | 本桌面项目的优先候选，重视分发修改版本时的源码开放 | 允许商业使用和收费分发；不要求普通网络服务仅因被访问就公开服务端改动 |
| AGPL-3.0 | 如果整套产品连服务端也开放，希望对修改后向用户提供网络服务的版本保留相应源码义务 | 仍允许他人合规经营竞争服务；需核对与各部分代码的兼容性 |
| Apache-2.0 / MIT | 优先降低采用门槛，接受自有独立部分进入闭源衍生产品 | 不能用它们重新许可已经受 GPL 约束的第三方部分；各文件保留其原有授权 |

GPL/AGPL 的具体 only / or-later 标识应按权利来源确定；这些是候选方案，本次没有替项目选定或写入许可证。不要加入“禁止商业使用”“禁止竞争”“衍生版本必须继续使用坚果”等额外条件后仍宣称标准开源。

仓库中已包含 GPL-3.0 的 v2rayN 源码，并有对应源码与许可证打包流程，这是良好的基础。接下来需完成：

- 记录该集成版本的来源、修改内容、版权声明和可重建步骤；不能只引用上游提交却忽略本地修改。
- 逐项核查实际打包的 xray、sing-box、mihomo、地理数据、.NET 组件及其他依赖的许可证和义务。复制 v2rayN-core-bin 仓库的总 LICENSE 不能自动代表每个二进制都已满足要求。
- Rust 主程序通过本机 HTTP 调用独立的 GPL 进程，不能仅凭“同包分发”就断言整个主程序必须 GPL，也不能仅凭“分进程”就断言没有衍生作品问题；按实际组合、来源和分发方式确定范围。
- Codex 官方桌面安装包、Codex++ 安装包、图标和品牌分别核验，不把本项目开源等同于拥有上游产品再分发权。当前仓库不能证明 Codex++ 安装包和全部插件的具体授权条件。
- 加入 THIRD_PARTY_NOTICES、组件版本/来源/许可证表和必要的对应源码。没有再分发依据的安装包改为从可信来源按需获取。

若未来采用双重许可，只能对拥有充分再授权权利的自有部分实施；不能对现有 GPL 上游代码直接出售闭源授权。社区贡献的授权也要提前讲清楚。

### P1：免登录使用与商业服务自然转化

src/main.ts:2594 启动时直接 renderLogin，安装和自定义供应商等本地能力也被登录页面挡住；65 行默认配置坚果。src/main.ts:160、lib.rs:2251、wallet.rs:4 将坚果地址固定在不同位置。

建议首屏改为“开始使用”“连接坚果服务”，未登录也能安装、配置自带 Key、安装公共技能和管理自己的代理。官方发行版可以保留清晰、可取消的坚果推荐入口，展示可核实的价格、服务状态和使用记录。

先做简单的模块拆分即可，不需要开发插件平台或拆成大量仓库：

- 通用模块：installer / providers / gateway / skills / proxy。
- 坚果模块：账号、钱包、订阅权益、商业服务说明。
- 通用资源配置：软件来源、校验信息、支持矩阵；应用即使无法访问坚果后台，也能使用独立的本地功能。

自建服务模式可以单独配置服务地址。官方支付、账号票据和凭证仍绑定官方可信来源，不能为了支持自建就取消当前支付域名校验，或把官方会话发给任意新地址。

### P1：下载来源和公开构建要可验证

lib.rs:2544 实际允许 HTTP；2622 行使 Codex++ 的 expected 校验值为空，其他产品的 SHA-256 也是可选。README 写 HTTPS，和当前代码不一致。Codex++ 无内置包时读取 GitHub latest，因此同一版本助手在不同日期可能安装不同上游版本。

建议默认 HTTPS；可信包清单记录版本、来源、哈希和平台，并验证适用的系统签名。哈希要来自可信发布渠道，和安装包一起被任意替换的哈希不能提供来源保障。若上游提供可信 digest/校验文件，应接入；没有时明确缺口，不能声称已经验签。

scripts/build-v2rayn-runtime.ps1 已固定源码/Core 提交，并核验 Core 的 Git blob 哈希，应保留；补充标准的发布 SHA-256 清单和构建指纹。当前“运行文件和 bin 存在就跳过”的缓存判定也应匹配源码版本和运行时，避免旧缓存进入新包。

tauri.conf.json:36 的 bundled/**/* 会广泛收集资源；Windows 便携脚本还会复制本地 codex/codexpp 目录。应改为明确的发布资源清单，校验无本机账号数据库、订阅、测试文件和未获授权安装包。Git 忽略文件不代表打包时也会忽略。

公开后增加 Windows/macOS 的干净检出构建与测试；保留已跟踪的 package-lock.json、Cargo.lock。第三方构建不应需要生产密钥，带签名的官方发布另走受保护的发布流程。当前 macOS 采用 ad-hoc 签名，正式分发需要相应签名与公证；还未看到应用自动更新实现，应先建立可信发布，再按需要增加更新能力。

### P1：权限、兼容性和收费说明保持诚实

- src/main.ts:67 默认启用完整访问，相关脚本会操作权限菜单并点击确认。建议默认关闭，使用者主动选择；原生确认留给用户。把恢复旧权限的操作补齐。这影响开源社区信任和支持成本。
- 强制中文通过本机 remote-debugging/CDP 和 Runtime.evaluate 注入实现，需要区分“原生中文设置”和“兼容补丁”；按适用版本启用并提供关闭方法。回环绑定是已有保护，但不等于调试接口已经具备完整认证隔离。
- gateway.rs:250 固定请求上游 stream: false，再把完整结果封装为 SSE，属于有限适配。当前 SSE 包装主要输出文本，不能承诺完整工具调用流、多模态或 Responses 全量兼容。优先使用上游原生 Responses；公开兼容测试结果。
- 本地网关和模型探测可能触发真实模型消费；提供明确的触发时机，并避免无提示的频繁健康探测。
- 界面“每天 5 点 / 每日 30G”是当前文案，启动检查又读 proxy_nut_daily_points；README 还提到每日扣费与每月流量上限。统一为服务端返回的费率和权益：点数折算、计费日时区、是否扣首日、日/月上限、免费范围、退款边界和断网行为。
- 使用说明写“仅限安装/必要连接”，界面同时提供浏览器与系统代理，实际可能影响其他应用。商业规则、用户说明和资源侧技术限制应一致，不能把用途声明当作技术隔离。
- README 还写 Windows/macOS 不改变系统代理，但 Windows 代码已经实现；密码登录接口描述也与 installer/login 不一致。开源前以当前实现重写支持边界。

## 4. 收入来源的取舍

| 收入来源 | 建议 | 需要的真实价值与边界 |
| --- | --- | --- |
| 坚果托管模型 API | 主要收入 | 明确价格、可用性、账单、额度限制、问题处理；收益来自上游采购与服务能力 |
| 托管配置、团队预算和管理 | 后续发展 | 只有当用户确有团队需求再建设；即使代码开放，托管、维护和服务承诺可以收费 |
| 官方安装协助、远程部署、企业支持 | 近期可做 | 按服务收费，说明交付范围；用户也能自行免费完成安装 |
| 官方签名构建与持续维护 | 增强转化和信任 | 官方来源、及时修复、兼容适配与支持；不以恶意阻止用户自行构建为前提 |
| 托管代理带宽 | 条件成立后再作为收入 | 先完成节点计费和免费通道隔离，核算最坏流量成本；否则优先让用户自带订阅 |
| 原创技能、行业方案、交付培训 | 可选 | 必须有原创或授权价值，不能把社区公开技能重新命名后宣称独占 |
| 捐赠、赞助 | 补充 | 不宜当作可预测的主收入 |
| 卡密解锁安装、本地网关或供应商切换 | 不推荐作为开源后的主收入 | 修改客户端即可移除门槛；免费可替代性高，会增加对抗和支持成本 |

建议首先保留一条简单路径：免费工具 → 用户自行决定是否连接坚果 → 购买真实模型额度或服务。无需在首轮制造复杂会员层级。

用毛利和服务成本检验方案，避免只看充值金额：

> 模型贡献毛利 = 已实际消费的服务收入 − 上游调用成本 − 支付与渠道费用 − 相关运行成本。
>
> 代理贡献毛利 = 已实际消费的网络服务收入 − 实际带宽成本 − 节点固定成本 − 滥用与渠道成本。

充值额同时对应未来待履约额度，不能直接当作利润。现有“5 点/天、30G/日”能否覆盖成本，需要结合每点收入、实际带宽采购价、重度用户比例和支持成本测算；本仓库没有这些数据，不能直接断言盈利。

开源后的关键观察项：免登录安装成功率、自带 Key 使用率、坚果连接和首次消费转化、付费复购、实际贡献毛利、每位用户支持耗时、无效支付与资源滥用。要接受一部分只使用免费工具的用户。

品牌策略独立于代码许可：可以制定官方名称、Logo、域名和签名的使用规则，要求衍生产品不冒充官方；不能借品牌规则限制许可证已经授予的合法修改、商业使用和再分发。保护生产域名、发布账号和签名比隐藏 API 地址更有效，公开地址不是秘密。

## 5. 按依赖顺序落地

### 第一阶段：确定是否具备公开条件

1. 确认开源范围是桌面仓库，还是连商业后端一起开放；核实自有代码和第三方权利。
2. 完成全部 Git 历史、已发布包和可追溯制品的敏感信息审计；发现过的有效凭证先撤销轮换，不能只删除当前文件。现有 .gitignore 是基础，不能替代这一步。
3. 核实模型扣费、支付和托管节点的服务端控制；完成上述 P0。若节点侧尚不可控，先关闭官方免费/付费节点供应，保留用户自带订阅。
4. 明确当前费率、免费范围、用量上限和账单规则，再修改界面与文档。

### 第二阶段：让公开版本能够独立使用

1. 增加免登录入口，提供可信默认安装源；本地功能不依赖坚果后台可达。
2. 归拢坚果服务接入代码与配置，保留清晰的可选入口；无需先大规模重构。
3. 默认关闭完整访问，区分中文原生配置和兼容补丁；补充配置备份恢复说明。
4. 增加项目 LICENSE、第三方声明、贡献说明、SECURITY、隐私与数据流说明、官方商业服务边界和品牌规则。

### 第三阶段：公开构建与运营验证

1. 干净环境完成 Windows 与 macOS 构建，核验打包清单和对应源码；公开构建步骤与限制。
2. 公开分支测试不使用生产凭证；签名与发布流程隔离，固定关键构建依赖版本。
3. 验证游客能安装、配置非坚果 Key、安装技能、管理自带代理；坚果服务中断时仍能使用本地功能。
4. 验证订单重放、越权查询、重复支付回调、并发扣费、免费安装通道、撤销节点凭证等资源边界。
5. 同时验证用户体验：不重复扣费、有可查账单、网络异常时不损坏配置、卸载和退出不残留错误代理。

现有 scripts/check-*.cjs 与 Rust 测试可继续使用；应补的是这些真实边界场景，尤其后台集成验证，不需要为每个文本改动堆测试。

## 7. 发布前的验收标准

- 用户没有坚果账号，也能正常完成核心本地流程。
- 用户修改客户端或使用其他客户端，也不能绕过官方模型和节点侧的付费权益。
- 公开源码、完整 Git 历史和发布包不包含有效生产凭证或个人数据。
- 下游知道哪些代码与素材由什么许可证授权，能拿到应提供的对应源码。
- 支付、余额、模型和代理扣费形成可解释且幂等的服务端账本。
- 官方版的优势体现在可信来源、稳定服务、可查账单、维护与支持；品牌与签名能够区分官方和衍生版。

只要这些条件成立，完全开放桌面功能与持续经营付费服务可以兼容。它不能消除竞争，也不能保证现有收入完全不变；它能把收入建立在持续交付的服务价值上，并降低依赖客户端保密带来的风险。
